# 财富模拟器 · uni-app 版

> 先测人格，再过一局人生 —— 8 道题算出你的「财运人格」，再用 5-8 分钟走完一局人生抉择，
> 看看你的财富剧本会走向哪一种结局。

本项目是《财富模拟器》的 **uni-app 实现**，可编译到 **H5 / 微信小程序 / App / 支付宝小程序** 等多端。

> 上游另有一个「微信小游戏 + Canvas 自绘」版本。两者的关系、以及这次融合做了哪些取舍，
> 见下面的 [与上游版本的差异](#与上游版本的差异)。

## 一、跑起来

### 方式 A：HBuilderX（推荐，零配置）

1. HBuilderX → 文件 → 打开目录 → 选 `D:\project\wh`
2. 顶部菜单「运行」→ 选择要跑到的端：
   - **运行到浏览器** → H5，改代码自动热更新，调试最快
   - **运行到小程序模拟器 → 微信开发者工具** → 需要先在设置里配好微信开发者工具的安装路径
3. 小程序端 AppID 留空时用测试号即可预览；上线前改 `manifest.json` 的 `mp-weixin.appid`

### 方式 B：命令行（Vue CLI / Vite 版 uni-app）

如果这个目录被当作 CLI 项目使用（`npm i` 后）：

```bash
npm run dev:h5          # H5 开发服务器
npm run dev:mp-weixin   # 编译到 unpackage/dist/dev/mp-weixin，再用微信开发者工具打开
npm run build:h5        # H5 生产构建
```

### 工具链（纯 Node，不需要装依赖）

```bash
npm run smoke           # 冒烟测试：逻辑链路 + 工程结构 + SFC 语法，共 146 项
npm run sim             # 跑 2 万局数值模拟，输出结局分布 / 属性分布 / 财运指数分布 / 分位数
npm run sim:100k        # 跑 10 万局
npm run tune            # 数值调参网格搜索
npm run test:reactivity # 响应式桥实测（85 项），需要 vue（npm i -D vue），没装会自动跳过
npm run check           # smoke + 5000 局模拟 + 响应式实测，提交前跑这个
```

> `test:reactivity` 是全项目风险最高的一环的专项测试，也是唯一需要 `vue` 的地方。
> 没装 vue 时它会打印提示并正常退出（不会让 CI 变红）。源码本身零依赖。

## 二、与上游版本的差异

上游版本是**微信小游戏**，本项目是 **uni-app**。这两者常被混为一谈，实际是完全不同的技术栈：

| | 微信小游戏（上游） | uni-app（本项目） |
|---|---|---|
| 界面 | 无 DOM / 无 CSS，全靠 Canvas 自绘 + 自己算触摸命中 | Vue 单文件组件 + rpx 流式布局，样式即 CSS |
| 布局单位 | 750×1334 虚拟坐标系，整体等比缩放 + 居中 | rpx（750rpx = 屏宽），配合 flex 自适应 |
| 平台 API | `wx.*` | `uni.*`（跨端统一），极少数平台特有 API 才分端写 |
| 目标平台 | 只有微信小游戏 | H5 / 微信小程序 / App / 支付宝小程序 |

### 因此这次融合改了什么

**一行没改的（17 个文件，逐字复制）**

```
core/   8 个逻辑模块 + registry.js
data/   config-loader.js + 7 张配置表
```

这 17 个文件原本就不引用 `wx.*`、不引用 `document`/`window`、不碰任何渲染 API —— 这是上游
「四层架构 + 逻辑层纯净化」的直接收益。所以它们**原样搬过来就能用**，包括离线数值模拟。

`npm run sim` 在新目录下跑出的分布与上游完全一致（S 12.12% / A 26.02% / B 43.10% / C 18.76%），
这本身就是「逻辑层确实零改动」的证明。

**重写的**

| 目录 | 上游 | 现在 |
|---|---|---|
| `platform/` | `wx-adapter.js` + `web-adapter.js` 两份 | 合并为 `uni-adapter.js` 一份，唯一碰 `uni.*` 的文件 |
| `components/screens/` | `src/render/screens.js`，755 行 Canvas 绘制 | 9 个 Vue SFC，每个界面一个文件 |
| `components/ui/` | `src/render/ui-kit.js` | 拆成 7 个可复用组件（按钮 / 卡片 / 属性条 / 属性 chips / 雷达图 / 结果卡 / 浮层） |
| `src/render/input-manager.js` | 自己维护矩形包围盒做命中检测 | **删除** —— DOM 事件模型自带命中检测 |
| `src/render/sfx.js` | WebAudio 现场合成 | `platform/sfx.js`，WebAudio 不可用时降级为 `uni.vibrateShort` 震动 |
| `src/render/app.js` | 渲染循环 / 缩放变换 / 相位路由 | **删除** —— 改成 `pages/index/index.vue` 里的 `v-if` 路由 |

**刻意保留 Canvas 的两处**

1. **雷达图**（`attr-radar.vue`）—— 五边形数据面用纯 CSS 做要么变形，要么依赖 `clip-path`
   在部分小程序端兼容性不稳，Canvas 反而是最稳的方案。它旁边永远并排显示属性条，
   所以即使某些机型上 Canvas 绘制失败，信息也不会丢。
2. **结果卡**（`result-card-canvas.vue`）—— 它的最终用途是「变成一张图片」发给朋友，
   所以天然就该是一张画布。这样「保存到相册」是所见即所得，不必引 html2canvas，
   也避免了「屏幕上好看、导出后错位」这个经典问题。

**音效的能力降级（需要你知晓）**

上游用 WebAudio 现场合成音效，零素材。uni-app 下这个方案只在 H5 / App 可用：
**微信小程序的逻辑层没有 WebAudio**，所以小程序端是「静音 + 震动反馈」。

震动反馈由引擎负责——每次抉择结算后 `game-engine.js` 会调 `adapter.vibrate(type)`，
小程序端因此不会出现「点了什么都没发生」的哑巴体验。

如果小程序端也要有声音，需要真音频文件（`uni.createInnerAudioContext` 不支持合成）。
音效文件建议压在 20KB 以内的短音，放 `static/audio/`，主包仍然远小于 2MB 限制。

## 四、架构：四层 + 单向依赖

```
components/ + pages/   表现层 Presentation（只渲染与输入，不含业务规则）
        ↓ 只读状态（经 composables/useGame.js）
    core/              逻辑层 Logic（纯 JS，零平台依赖，可 Node 离线跑）
        ↓ 读配置
    data/              数据层 Data（纯数据 + 配置加载）
        ↑ 平台能力
  platform/            平台适配层（唯一直接调 uni.* 的层）
```

这套分层在 uni-app 下比在小游戏下**收益更大**，因为目标平台从 1 个变成了 4 个：

1. **逻辑层不认识 `uni.*`，也不认识 Vue。** 所以 `tools/simulate.js` 能直接 `require` 同一套代码跑 10 万局 —— 数值平衡不靠拍脑袋。
2. **加一个端只写一个适配器。** 想再上鸿蒙或抖音小程序，写个新 Adapter 就行，玩法代码一行不改。
3. **玩法全部数据驱动。** 加事件、改数值、加人格，都只动 `data/tables/` 下的配置表。

`npm run smoke` 里有专门的静态检查守住这条线：一旦有人在 `core/` 或 `data/` 里写了 `uni.`，
测试立刻失败并指出文件名。架构约束不靠自觉，靠 CI。

## 五、引擎 ↔ Vue 的响应式桥（`.workbuddy` 之外最容易踩的坑）

`composables/useGame.js` 值得单独说明，因为它是这次融合里**技术风险最高**的一环。

`GameEngine` 是一个可变对象：它持有 `this.state` 并直接改写它，`replay()` 甚至会整个替换。
三种直觉做法都会出错：

| 做法 | 后果 |
|---|---|
| `reactive(engine.state)` | `replay()` 后 `this.state` 指向新对象，代理还盯着旧的 → **界面再也不更新** |
| `computed(() => engine.state)` | 返回的永远同一个引用，Vue 的 `hasChanged` 判定「没变」 → **点了没反应** |
| `reactive(engine)` | Vue 递归代理整个引擎（含全部配置表） → 性能损耗 + 破坏引擎内部引用相等判断 |

**采用的方案：快照 + markRaw**

- 每次调用引擎动作后，把状态**浅拷贝**一份塞进 `ref`。新对象 = 引用必变 = 组件必然重渲。
- `attrs` / `collection` 这两个会被原地修改的字段单独再拷一层，避免子组件拿到陈旧引用。
- `engine` / `sfx` / `adapter` / `config` 用 `markRaw()` 排除在响应式系统之外（它们本来就不需要）。
- 整个返回对象用 `reactive()` 包一层，这样模板里能写 `game.state.phase`，不用到处写 `.value`。

代价是每次操作多一次小对象拷贝（几十个字段），对这个体量的游戏可以忽略。
换来的是**逻辑层一行不用改**。

还有一处容易忽略的细节：`quizProgress` / `currentQuestion` 这些 computed 里，开头都有一句
看起来毫无意义的 `state.value;`。它其实是必需的 —— 答题进度只存在 `engine.quiz` 这个
**非响应式**对象里，不碰 `state.value` 的话 Vue 认为没有任何依赖，会把结果永久缓存，
表现为「题目永远停在第一题」。代码里对此有注释，**不要顺手删掉**。

## 六、数值平衡怎么调

数值系统有三层，改哪一层得到什么效果是明确的：

```
① 事件表 data/tables/event.js        —— 「这个选项值多少钱」，人类可读的整数
        ×
② 标定表 data/tables/balance.js      —— 全局松紧（现金收益/损失、其他属性收益/损失、生活开销 5 个系数）
        =
③ 结局阈值 core/ending-judge.js      —— S/A/B/C 卡在哪儿 + 财运指数档位
```

**调参流程：**

```bash
node tools/tune.js --n=3000     # 1) 自动搜索最接近目标的标定系数
                                #    目标：现金分位数 p20=35 / p65=55 / p92=80
# 2) 把系数抄进 data/tables/balance.js
# 3) 把建议阈值抄进 core/ending-judge.js 的 GRADE_RULES
npm run sim                     # 4) 复核评级分布
# 5) 看【财运指数分布】那一节，如果分位或档位命中率偏了，
#    回头改 core/ending-judge.js 的 INDEX_ANCHORS 与 INDEX_BANDS
```

> 关键经验：**不要以「评级分布」为优化目标**，因为阈值本身也在变，搜索会追一个移动靶。
> `tune.js` 优化的是与阈值无关的**分位数**。另外它启动时会把 `balance.js` 置为全 1，
> 否则标定系数会和搜索系数叠加成双重缩放。
>
> 另一条经验：**收益/开销的松紧和「指数刻度」是两件独立的事。** 改完数值后评级分布可能
> 还达标，但财运指数的分位已经漂了 —— 所以 `simulate.js` 把两者分开打印。
> 这也是为什么 `smoke.js` 有一条断言直接钉住 `INDEX_ANCHORS`：漏了这一步会立刻被抓住。

**当前实测分布（3 万局）：**

| 结局 | S | A | B | C |
|---|---|---|---|---|
| 实测 | 12.1% | 26.0% | 43.1% | 18.8% |
| 目标 | 8% | 27% | 45% | 20% |

属性终值均值：现金 53.4 / 人脉 62.6 / 认知 70.1 / 胆识 61.3 / 运势 57.4

其他关键机制：
- **生活开销（upkeep）**：每个事件扣一点现金。这是数值系统的「重力」—— 没有它，玩家一路选正向选项，现金必然顶到 100，所有局都变成 S 级。
- **保底机制**：连续 2 次负向事件后，第 3 次强制出正向 / 机遇事件，防止「必输局」。
- **人脉托底**：人脉 ≥ 75 时，现金损失减半。阈值定在 75 而不是 60，是因为实测人脉很容易通胀到 70，阈值太低会让这条规则几乎全程生效，把整个数值系统的下行压力抵消掉。

## 七、v1.1 ~ v1.3 新增：让玩家愿意回来

上游版本的核心问题是**「一局玩完就没有回来的理由」**：单局 5-8 分钟，玩完看到一张结果卡，
然后就没有然后了。这一版补了四块内容，每一块都对应一个具体的留存/分享动机。

### 1. 图鉴：人格 10 条 + 结局 43 条，永久保存

- 入口在首页底部的图鉴卡片，**随时可进、看完就回**，不影响正在进行中的对局
  （引擎在开关图鉴时完全不碰 `attrs` / `stageIndex`，这一点有专门测试守着）。
- **人格图鉴**：2 列网格。未解锁的显示灰色「?」+ 虚线边框，已解锁的显示徽章、名称、
  一句话描述，点开有详情（含这个人格的初始属性偏向）。
- **结局图鉴**：按 10 个人格分组，每组有 S/A/B/C **四个独立解锁位**，
  这样「收集」的粒度是 43 个而不是 13 个 —— 数量本身就是复玩动力。
  点开详情能看到已解锁等级的旁白原文，未解锁的显示「尚未抵达」。
- **隐藏结局**单列一区（3 条），解锁前只显示「?」。

**设计要点：43 个结局的解锁进度存在 `collection` 里，与存档分离。**
重开一局、清掉存档都不会丢图鉴 —— 这是「长期收集」能成立的前提。

### 2. 答题可以返回上一题

原本答错一题只能重开。现在：

- 答题页左上角有「‹ 上一题」，第一题时置灰（点了给提示而不是静默失败）。
- 退回去时**上次的选择会高亮并标注「已选」**，玩家一眼就知道自己原来选了什么。
- 建号页（人格已揭晓那一页）底部还有一行「答错了？回去改一下答案」，落在最后一题，
  可以继续往前退。

**实现上有个坑值得记下来：回退必须同时满足两条看似矛盾的语义。**

| 需求 | 数组 | 回退时 |
|---|---|---|
| 分数只能由「已确认的作答」决定 | `answers` | **截断** —— 保证 vector 恒等于 `answers[0..index-1]` 之和，不存在歧义 |
| 界面要记得上次选了什么 | `lastChoice` | **不截断** —— 否则玩家退回去看到一道空白题，会以为答案丢了 |

早期版本把两者合并成一个数组，结果是「已选」高亮**永远不生效**（退回去的那道题，
它的作答正好被截断了）。分开之后由测试把两条语义分别钉死。

计分采用**存原始选择 + 回退时从零重算**，而不是在 vector 上做减法。
减法是最容易出错的做法（连减两次、漏减都会让分数静默偏移），8 题的量级下重算是常数开销。

### 3. 每日财运签（首页，每天零点换一支）

中文语境里最不需要解释的载体：不用教程，玩家一看就懂，而且天然愿意截图。

- **同日幂等**：种子 = `hash('ws-fortune-' + 'YYYY-MM-DD')`，所以同一天无论刷新多少次
  都是同一支签。这一条很关键 —— 如果下拉一下就变签，玩家立刻会认为这东西在骗人。
- **跨天自动换**，不需要服务端、不需要定时器。App / 小程序长时间驻留后台时，
  `sync()` 会顺手检查是否跨天（`refreshDaily(false)` 在同一天内直接命中缓存，零开销）。
- 每支签包含：签文等级（大吉/中吉/小吉/平/小凶）、今日财运指数、一句签文、
  宜 2 条 / 忌 2 条、幸运色 / 幸运数字 / 幸运方位。首页可展开收起。
- **签文与数字强制自洽**：每个等级自带 `indexRange`，指数从区间内取，
  绝不会出现「大吉 + 指数 25」这种一眼假的结果。这条不变式有测试守着。
- **文案刻意只写生活建议，不写投资建议。** 「今天适合加仓」既不合规也不负责任；
  「适合把拖了很久的一件事做完」才是安全的写法。

### 4. 财运指数：让结果像一份测试报告

原本结果只有一个 S/A/B/C 字母。字母是**名次**，只回答「你比多少人好」，
而且判定里带硬门槛（现金不到 89 就绝无可能是 S）—— 玩家拿到 C 容易归因为「这局运气差」，
而不是反思自己的选择。

现在并列展示两个东西：

- **等级（名次）**：S/A/B/C
- **财运指数（分数）**：0-100 的连续分 + 档位文案（财神眷顾 / 财运不错 / 中规中矩 /
  略显拮据 / 急需转运）
- 外加 **2 个人设标签**（按终值最高的两个属性给：现金流敏感 / 人脉为王 / 长期主义 /
  敢想敢干 / 运气加持）

**指数必须做标定**，这是实际踩出来的：直接加权求和得到的是属性均值的线性映射，
而属性均值的实际分布非常窄 —— 实测 20 万局，原始分均值 60.3、标准差只有约 12、极差仅 32~87。
不拉伸的话玩家永远只看到 48~75 这一段数字（等于没有区分度），而且最高档只命中 1%、
最低档一次都不出现（档位形同虚设）。

所以按实测分位做了线性拉伸：原始 p50(60.3) → 50，原始 p92(73.5) → 80。
标定后分布变成 **7.0% / 21.1% / 37.0% / 27.2% / 7.7%**，均值恰好 50、跨度 0~100。

锚点写在 `core/ending-judge.js` 的 `INDEX_ANCHORS`，并有一条测试断言它精确成立 ——
**改了 `event.js` / `balance.js` 却没重跑模拟重新标定，测试会立刻失败。**

### 5. 本局新解锁的即时反馈

`_unlock()` 除了写进 `collection`，还会把「本局第一次拿到的」记进 `newUnlocks`，
结局页据此显示「本局新解锁」横幅，并给一个「去图鉴看看 ›」的入口。

判断必须发生在 push 之前 —— 集合本身不带时间戳，push 完就再也分不清
这一条是老收藏还是刚拿到的了。

### 6. 等级文案：让字母后面有话可说

光给一个字母太冷，玩家不知道自己这一局到底算什么水准。现在每个等级都配了一句话：

| 等级 | 说明 |
|---|---|
| S | 天时地利人和 |
| A | 稳健扎实 |
| B | 平稳度日 |
| C | 遗憾剧本 |

键名规则固定为 `grade` + 等级字母，界面用 `t('grade' + quality)` 拼出来，
以后要加等级（比如 SS）只要在 `data/tables/text.js` 补一行，界面不用动。
隐藏结局复用同一套渲染，但会单独显示成「隐藏结局」。

**这一条其实是修一个遗留缺陷。** 原来结局页渲染的是 `{{ quality.label }}`，
而 `QUALITY` 表（`utils/canvas-kit.js`）里只有 `color / bg / border`，
**根本没有 `label`** —— 于是等级说明那一行在页面上永远是空白的。
编译不报错、`node --check` 不报错、原有测试也全部通过，只有肉眼盯着界面才会发现。
`text.js` 里那个定义了却从没被引用的 `negNote: '遗憾剧本'` 就是它的原设计意图。

所以顺手补了两道防线（冒烟测试新增分组 O）：

- 每个等级都必须有非空说明文案；
- 扫描 `components/` 与 `pages/` 下所有 `.vue`，把 `t('xxx')` 里的字面量键逐个回查文案表。
  `t()` 查不到键时会**把键名原样返回**，也就是漏文案不会报错、只会在界面上冒出
  一串 `gradeA` 这样的半截英文 —— 静态扫描能在提交前拦下来。
  （`t('grade' + g)` 这类动态拼接会跳过，静态看不到全貌，硬查必然误报。）

### 7. 阶段里也能返回上一件事（v1.2）

测试的 8 道题能退回去改，阶段里的 14 次抉择却不行 —— 这是最容易被玩家骂的地方：
看到结算才发现上一件事选错了，而人生模拟最劝退的情绪正好在**看完阶段评级那一刻**。

现在每个阶段都有「返回上一件事」，出现在三个位置：

| 位置 | 文案 | 作用 |
|---|---|---|
| 阶段页左上角 | ‹ 上一件事 | 退到上一件事重选（和答题页同一个位置，玩家不用重新找） |
| 结算浮层 | 换一个选择 | 看到后果才想改，是最常见的场景 |
| 阶段结算页 | 上一件事选错了？回去改一下 | 看到评级才后悔，一定要给回头路 |

#### 实现：整帧快照，不是反向扣分

一次抉择会同时改动 **八处**状态：属性、flags、连锁队列、保底计数、已抽集合、
阶段内计数、历史记录、随机数状态。想靠反推把每一处都还原，只要漏掉一处
（最容易漏的是保底计数），就会留下一个**永远查不出来的偏移**——
不抛异常、分布看不出异常，只有细心的玩家觉得"怎么感觉怪怪的"。

所以 `chooseOption()` 的第一件事（必须在任何改动**之前**）是压一帧完整快照，
`stageBack()` 弹出一帧整体覆盖。一局最多 14 帧，代价可以忽略。

**随机数状态也要一起还原**。这样"退回去重选同一个选项"会得到完全一样的后续事件，
玩家不会觉得"我只是想改一下答案，怎么整个世界都变了"。

#### 同一个动作覆盖两种场景

- 站在第 N 件事还没选 → 撤销第 N-1 件事的抉择，回到第 N-1 件事
- 刚选完、结算浮层还开着 → 撤销这一次抉择，**留在原地**重选

它们在数据上是同一件事（都是"弹出最近一帧"），所以合成一个 `stageBack()`。
跨阶段也成立：刚进第 2 阶段时按返回，回到的是第 1 阶段的最后一件事
（`stageIndex` / `eventsInStage` / 阶段快照一起回滚）。

#### 不存档，翻盘清空

回退栈**不写进存档**：读档后玩家落在"某个事件、尚未选择"，栈本来就是空的，
语义干净。翻盘则必须**主动清空**——翻盘等于这一阶段重来，
旧快照记录的是另一条时间线上的属性，退回去会得到一个既不属于旧时间线、
也不属于新时间线的混合状态。

### 8. 一键回首页（v1.3）

小程序没有浏览器返回键。玩家在某一屏想回首页，只能杀进程重开 —— 这已经不只是体验问题，
而是**数据问题**：重开一次等于把当前这一局丢掉。所以现在每个界面底部都有一个「回首页」。

入口只有一处定义：`components/ui/ws-home-foot.vue`。不在各屏各写一份，理由有两条 ——
位置与留白会飘，更重要的是「回首页到底做了什么」必须只有一处说法。

| 加在哪 | 怎么加的 |
|---|---|
| 答题 / 阶段 / 图鉴 | 页脚自带 `margin-top: auto`，吸在屏幕最下方 |
| 建号 / 阶段结算 / 结局 / 结果卡 | 主操作按钮已经吸底了，页脚改成紧跟其后（同时存在两个 `auto` 会把空白平分，两边都不到底） |
| 首页 / 隐私页 | **刻意不加**：首页本身就是家；隐私页在进游戏之前，在那儿能「回首页」等于绕开用户协议 |

#### 顺手定死了「存档什么时候存在」

加完按钮才发现，真正的风险不在按钮，而在**回首页之后首页会给什么**。
首页那句「继续上次的人生」取决于存档在不在，而存档的有无会被三处动作改变：

| 时机 | 处理 | 原因 |
|---|---|---|
| 每次抉择 / 进阶段 | 写存档 | 这就是可续玩的进度 |
| 开新的一局（`startTest`） | **清掉** | 开新局 = 明确放弃上一局。不清的话，玩家答到第 3 题时回首页，「继续上次的人生」会把他拉回上一局的残局 —— 两局状态混在一起，是最难解释的一类 bug |
| 结局判定（`_judge`） | **清掉** | 一局已经结束，没有可续玩的进度了。不清的话，玩完回首页会看到「继续上次的人生」，点进去被拉回终局前那一刻，再点一次「继续」会重新判一次结局、`playCount` 又 +1 |

`goHome()` 本身**保持纯导航**：不写存档、也不清存档。存档的生命周期由「一局的开始
与结束」决定，不该由「我看了一眼首页」决定 —— 导航函数带破坏性副作用，是那种平时
没事、某个入口多点一次就吃掉玩家进度的隐患。所以在阶段中途回首页是安全的：存档还在，
首页会给出「继续上次的人生」，续玩时属性与事件与离开那一刻逐字节一致。

**`hasSave` 统一挂在 `sync()` 上刷新**，而不是在几个「显而易见的」动作里逐个补。
它读的是本地存档、不在 Vue 的响应式依赖里，漏掉任何一条路径，首页就会出现一个点下去
报「存档已失效」的死按钮 —— 那比不显示按钮更让人困惑。

### 9. 选项卡：让「选」这个动作有手感（v1.3）

原来答题的选项是一条浅色横条，按下只是整条变金。现在有三层：

- **左侧字母徽标 A / B / C** —— 选中那一条的徽标从灰描边变成金色实心。
  位置固定，余光扫视时最先看到的就是它。
- **卡片化** —— 白底 + 描边 + 极淡投影（选中时投影转成暖金），
  比「一片色块」更像一个能按的东西。
- **勾选记号** —— 选中后右侧出现一个勾。它是用**两条边框拼出来的**，不是「✓」字符：
  U+2713 在 iOS / 安卓 / 小程序三端的字体回退各不相同，有的窄体、有的带基线偏移，
  对不齐卡片中线。

三层信号叠加是有原因的：只有「变金色」这一层的话，色弱玩家或阳光下的屏幕都可能看漏。

**点击监听刻意不绑在这个组件上**，而是由调用方在外面包一层普通 `<view @tap>`。
理由是个跨端陷阱：在自定义组件上绑 `@tap`，H5 端的「组件 `$emit` 的同名事件」与
「原生 DOM 事件的冒泡」可能同时命中父级监听 —— 一次点击跑两遍，放在答题页就是
**连跳两题**。点得快时几乎看不出来，只有慢慢点才发现。挂普通 view 两端都只有冒泡
这一条路径，行为一致。`hover-class` 则留在组件内部：它作用于被按到的元素本身，
不依赖事件绑定，谁在外面包了一层都不影响按压反馈。

入场时四条选项按 45ms 逐条浮起（延迟上限压在 135ms —— 再长就会被感知成「点了没反应」，
而它只是装饰，不能拖慢可点性）。动画的 `@keyframes` 写在**非 scoped** 的样式块里：
scoped 样式靠 `[data-v-xxx]` 属性选择器匹配，各端编译器对动画名的改写并不一致，
一旦动画名被改写而 `animation` 声明没有，动画会静默失效。即使真的失效也只是没有
入场动效，选项本身照常显示，不影响可用性。

答题页与阶段抉择页**共用同一个组件** `components/ui/ws-option.vue`。各写一份的后果
不是编译不过，而是改了一处的金色忘了改另一处 —— 测试抓不到，只能靠人盯着看。
所以 smoke 里直接禁止这两屏保留自己那份选项样式。

## 九、一局长什么样

```
隐私弹窗 → 首页（每日财运签 + 图鉴入口）
   → 财运人格测试（8 题，可返回上一题改答案）→ 建号（人格 + 初始属性 + 雷达图）
   → 第 1 阶段 初入社会（3 个事件）
   → 第 2 阶段 积累期（4 个事件）
   → 第 3 阶段 转折期（4 个事件）
   → 第 4 阶段 收尾期（3 个事件）
   → 结局判定（S/A/B/C 或隐藏结局）+ 财运指数 + 人设标签 + 新解锁提示
   → [C 级触发翻盘：看 1 次激励视频，回退第 4 阶段重选]
   → 结果卡（人格 + 结局 + 财运指数 + 雷达图 + 全服百分比 + 小程序码）→ 保存 / 分享 / 再玩
```

单局 14 次抉择，约 5-8 分钟。中途退出会自动存档，下次进入首页提示「继续上次的人生」；
在阶段中途按底部「回首页」也不会丢进度，回来时属性与事件和离开那一刻完全一致。

首页 ⇄ 图鉴是一个随时可进出的旁路，不占进度、不影响对局。

每一屏（首页与隐私页除外）底部都有一个「回首页」。

## 十二、已知的平台差异与注意事项

1. **小程序 canvas 是原生组件，层级高于普通 view。** 结果卡所在页面的 Toast 理论上可能被
   画布遮挡。当前布局下两者不重叠（卡片居中、Toast 贴底），但如果以后调整布局要留意。
   彻底解决可改用 `canvas type="2d"`（基础库 2.9.0+ 支持同层渲染）。

2. **`canvasToTempFilePath` 必须带组件实例。** 所以「canvas → 图片」这一步写在
   `result-card-canvas.vue` 内部，`platform/uni-adapter.js` 只负责「文件 → 相册」。
   这个职责切分是必需的，不是随意划分的。

3. **微信小程序不允许用 API 主动拉起分享面板。** 必须由用户点击
   `<button open-type="share">` 或右上角菜单触发。所以结果页按平台切换实现：
   小程序端用 `open-type="share"`，H5 / App 端复制文案到剪贴板。
   分享文案在页面层 `onShareAppMessage` 与按钮共用同一个构造函数，保证两处一致。

4. **`package.json` 刻意不写 `"type": "module"`。** 因为 `tools/` 下的脚本用 `require()`
   加载 `core/`、`data/`，一旦声明 ESM，这些脚本立刻就废了。同理，`core/`、`data/`
   下的模块继续用「IIFE + globalThis 命名空间」而不是 ESM 的 import/export ——
   一份文件两种加载方式都能吃。加载顺序由 `core/index.js` 和 `data/index.js` 集中维护。

5. **新增核心模块时别忘了挂载。** `core/` 下新加文件后，必须在 `core/index.js` 里补一行
   `import './xxx.js'`，否则打包器不会把它纳入依赖图（H 组检查会自动发现这个问题）。

6. **全局对象兜底必须显式列出 `global`。** 抖音小程序（TMA）的模块作用域里
   `globalThis` / `window` / `self` 都不存在，只有 `global`；而打包器会把源码里的
   `this` 兜底编译成 `void 0`。所以 `core/`、`data/` 下每个 IIFE 的结尾，以及
   `core/index.js`、`data/index.js` 取命名空间时，都统一写成
   `globalThis || self || window || global` 的显式兜底链，不能依赖 `this`。
   微信端 `globalThis` 存在，走第一条分支，行为不变。
